## Problem Statement

Connect an existing OpenClaw instance to Microsoft Teams using an existing user account. The operator cannot register an Entra application, Azure Bot, or Teams app. People must be able to converse with OpenClaw in direct messages and selected group chats. Publish reusable source on GitHub without organization-specific settings or credentials.

## What Makes This Cool

People use an ordinary Teams conversation to reach their existing assistant. Operators configure their own account and OpenClaw endpoint without provisioning a bot registration.

## Constraints and Approved Premises

- Teams only. Support text in DMs and selected group chats; defer channels, files, calls, reactions, edits, and proactive messages.
- Interactive browser sign-in and occasional operator reauthentication are acceptable. Do not store a password in configuration.
- Configuration covers account identity, access lists, group triggers, and OpenClaw connection details. Credentials and runtime data stay outside Git.
- The user approved approach B: a modular standalone bridge with replaceable Teams transport, initially evaluating teams-api.
- Engineering review decisions: retain the full modular scope, but validate the transport first; deploy the bridge on the same EC2 host as OpenClaw, using a private SSH/SSM path for interactive browser access and loopback for Gateway requests.
- This is an experimental user-client integration until tenant tests pass. No claim of Microsoft-supported bot behavior or indefinite unattended authentication.

## Research and Approaches Considered

The [SidU setup project](https://github.com/SidU/openclaw-teams-setup) creates Azure resources and an application registration. [OpenClaw Teams setup](https://docs.openclaw.ai/channels/msteams/setup) also requires registration, including its Azure-subscription-free path. Neither satisfies this operator's constraint.

[teams-api](https://github.com/Maxim-Mazurok/teams-api) documents interactive browser authentication and chat read/send operations. It is a candidate, not a dependency already validated in this tenant. Review its source, license, credential handling, pagination, timestamps, and error behavior before pinning a version.

### A: Small relay
One process directly combines polling, filtering, OpenClaw requests, and replies. Small effort and useful for a feasibility experiment, but recovery and transport changes become tangled. Reuses teams-api.

### B: Modular standalone bridge, selected
One deployable Node.js/TypeScript process with separate Teams adapter, policy/router, OpenClaw adapter, and SQLite persistence. Medium effort; improves recovery and testability without introducing distributed services. Reuses teams-api initially and OpenClaw's documented HTTP interface. Transport compatibility remains the main risk.

### C: Browser UI automation
Keep a browser open and operate Teams through its UI. Higher effort for reliable background monitoring because navigation, virtualized history, and UI changes complicate message discovery. Reuses browser tooling but requires a new message adapter. Deferred fallback, not a second implementation in v1.

## Recommended Approach

Flow: Teams polling → normalize messages → access/trigger checks → durable queue → OpenClaw → durable reply → same Teams conversation.

### Components

1. Teams adapter: interactive login, authenticated identity, conversation discovery, paginated message reads, normalized IDs/text/mentions, and sends. Expose capabilities explicitly; missing mention support must never silently become reply-to-all.
2. Router: accept only configured conversations and senders, suppress self/system messages, apply group trigger, and assign a stable session identity.
3. OpenClaw adapter: authenticated request/response with timeout, fixed destination agent, and chat-specific session identity.
4. SQLite store: per-account/conversation cursor, unique inbound message IDs, queued requests, saved completions, reply parts and delivery status. One process owns the database using an exclusive process lock.
5. CLI: configure, login, list chats, run, status/doctor, and inspect/reconcile uncertain deliveries. Names are design proposals, not existing commands.

Engineering review: the bridge owns the small Teams HTTP read/send surface, reusing the candidate library's authentication and parsing only where their contracts are validated. Do not use its high-level request wrappers unchanged. Set AbortSignal deadlines on actual requests and cancellation during shutdown; retries belong to the scheduler, not a hidden library loop. Validate pagination origins/paths and disable automatic redirects before forwarding credentials. Return structured rejected/retryable/auth-expired/uncertain outcomes rather than raw exceptions. Ambiguous write results are never automatically retried. Pin the reviewed dependency version and verify its shipped package exports before relying on helper imports; do not depend on undocumented deep imports or fork the whole library.

Validate normalized messages and paging metadata at the adapter boundary. Require nonempty stable message/sender IDs, parseable service timestamps, supported content types and bounded field sizes. Explicitly recognized system events may be ignored; malformed message events must not be silently filtered as system events. A malformed message or pagination response pauses only that chat, preserves its cursor and presents a sanitized reason for operator review. Never derive fallback IDs from message text or display names. Configuration, adapter and storage share one definition of the normalized message and structured error contracts.

### OpenClaw integration

Use the optional [Chat Completions HTTP endpoint](https://docs.openclaw.ai/gateway/openai-http-api), subject to verification against the installed OpenClaw version. It requires enablement and gateway authentication. Set a fixed configured agent/model and a stable `user` value derived from deployment namespace, authenticated Teams account ID, and conversation ID. Send each accepted turn once and let OpenClaw retain session history; do not resend the entire Teams history.

DM sessions are per conversation. Each group has a shared session, with sender identity included as untrusted message metadata. Only triggered group messages enter the session. Conversation separation does not isolate an agent's filesystem, tools, or global memory: use a dedicated OpenClaw agent with resources suitable for everyone on the allowlist. Do not route to a personal main session. Verify this isolation and memory behavior in the installed version.

Prefer loopback or a private connection to OpenClaw; require HTTPS for remote endpoints except an explicit development override. Gateway credentials come from a named environment variable or protected secret file, never a command-line argument. Redirects must not forward authorization to a different host.

The documented shared-secret endpoint grants owner-level turn semantics; a sender ID in text is not an authorization boundary. All allowed senders must be trusted for the dedicated agent's full capabilities. If that cannot be accepted, block deployment until a restricted gateway/agent environment is provisioned; chat session separation alone is insufficient. Do not claim the bridge inherits native channel approval or sender-permission rules.

### Conversation behavior

- Default deny. DMs require an allowed sender ID. Groups require an allowed chat ID and an allowed sender ID. Names are display-only; configuration uses stable IDs selected from discovery.
- Groups respond to a configured command prefix, default `!claw`, or a real mention of the authenticated account. Prefix-only is a supported mode if mention metadata is unavailable. Advertise mention support only after validation.
- Ignore the account's own messages, system events, reactions, deletions, and previously seen IDs. Treat edits as updates to an existing ID, not new turns.
- Replies go to the immutable source conversation ID. Model output cannot choose a destination, change policy, or issue bridge commands.
- Process one request at a time per chat. Permit bounded concurrency across chats (default 2). Cap pending work (default 100 globally, 20 per chat); pause ingestion without advancing its cursor if full.
- Convert incoming HTML to text without loading remote content. Escape outgoing text; split long responses at paragraph boundaries with numbered parts. Start with a conservative 3,000-character limit and verify service limits. No streamed partial edits in v1.

### Polling, restarts, and delivery

Poll allowed chats at a configurable interval (default 5 seconds), with bounded pagination, jitter and backoff. Discover new eligible DMs every 60 seconds. On initial activation of each chat, establish a baseline and do not answer old history. On subsequent starts, resume from persisted state. Fetch with overlap, deduplicate by account/chat/message ID, and enqueue oldest first. Advance the cursor transactionally only after durable recording. If pagination cannot reach the saved boundary, report a history gap and pause that chat rather than skipping messages.

Use one in-process Teams request scheduler with a configurable account-wide request budget and at most two in-flight requests by default. Count discovery, every page, identity checks and sends against the budget. Rotate reads fairly across eligible chats; replies have bounded priority so they cannot starve reads. Limit pages per chat per turn and retain a durable scan continuation until all earlier messages are collected before enqueueing newer ones. Do not advance the processing boundary based on a partial newest-first page scan. Validate continuation links again on resume. Account throttling delays all eligible work; honor Retry-After and apply bounded jittered backoff. Stop new ingestion when queued work is full, while retaining explicit status and recovery operations. The request budget is an operator-set load limit, not a claimed Microsoft quota.

Use indexed unique account/chat/message keys and indexed job-state/next-attempt/chat-order lookups. Stream bounded pages instead of loading whole chat histories into memory. Run payload cleanup in small batches and expose request-budget delays, oldest job age, last poll, throttle state and queue depth without logging bodies. Detect disk-full/DB failure and stop cursor advancement.

Initial activation persists a cutoff before the first read, using a verified service-clock timestamp (or a documented snapshot cursor if available). Ignore messages strictly older than that cutoff; ingest all messages at or after it, including arrivals during pagination, using IDs to distinguish equal timestamps. Retry an interrupted activation with the same saved cutoff. If the transport cannot provide a reliable cutoff, fail activation and resolve that capability before release. Test arrivals during discovery, pagination and activation restart.

Store states: queued → invoking → response_ready → sending → sent, with failed and uncertain states. Persist the final response before sending. A confirmed retryable rejection can be retried with capped exponential backoff and Retry-After support. An OpenClaw timeout after submission may have executed tools; mark uncertain and do not automatically invoke again. A Teams timeout after submission may already have sent a reply; attempt reconciliation using a returned/correlated identifier if supported, otherwise require operator resolution. Content matching alone is insufficient proof. Crashes during invoking/sending follow the same uncertain-state rule. Exactly-once external execution is not promised.

Persist each reply part independently. Do not resend confirmed parts after restart. Pause the affected chat while an uncertain turn is unresolved so later turns do not overtake it. Operator reconciliation offers mark-complete, cancel, or explicitly retry with a duplicate warning. Recheck access policy before invoking and before sending; revoked access cancels pending work. Deleted chats fail locally without rerouting elsewhere.

Authentication expiry transitions the service to needs-login, preserves pending work, and reports actionable local status. Reauthentication must verify the same account before continuing; another account needs a separate state namespace. Never loop on password/MFA prompts in a background service. Retry transient reads safely; do not treat 403 access denial as a reason to keep retrying forever.

Terminal failure pauses its chat and appears in local status with a sanitized reason. Operator cancellation advances past that turn; retry is explicit. Do not automatically send extra error messages through an unreliable Teams connection.

### Configuration and local data

Versioned JSON configuration, validated at startup; reject unknown fields and invalid values. Precedence: explicit config-file path, named environment secret overrides, documented defaults. Settings include account hint, state directory, OpenClaw URL/agent/secret reference, DM sender IDs, group chat and sender IDs, trigger mode/prefix, polling, timeout, queue limits, and reply length. Account identity is verified from login, not trusted from a display name.

Ship placeholder examples only. Store browser profile, token cache, database and logs under an OS-appropriate user state directory. The approved EC2 mode explicitly uses protected-file storage under a dedicated service user on an EBS volume (encryption waived by operator on 2026-10-02): directories 0700, credential files 0600. Validate ownership and permissions before reading/writing; fail on unsafe permissions, symlinks, or storage-mode mismatch. Do not silently switch between keyring and file modes. Document that the service user and host administrators can read these credentials. Secure browser access and credential persistence across reboot remain required validation checks.

Logs contain event categories, counts, durations and redacted correlation IDs, not credentials, message bodies or raw transport exceptions. Pending message bodies are retained only while needed; purge completed payloads after 24 hours by default. Retain minimal deduplication records for 30 days; cursor boundaries prevent older history from being replayed after pruning. Local status exposes queue depth, last successful poll, needs-login, history gaps and uncertain jobs. No public dashboard or telemetry in v1.

Canceled and terminal-failure bodies also expire after 24 hours. Queued and uncertain bodies expire after 7 days, configurable: purge their content, preserve the minimal IDs/status, mark expired and require operator resolution before that chat resumes. Manual purge is available. Cleanup includes SQLite WAL/checkpoint handling; document that logical deletion does not guarantee forensic erasure of disk or backups.

The first transport experiment must inventory every credential-bearing file, including browser cookies/profile databases and the library's own token caches. Both extracted tokens and browser state follow the explicit protected-file policy on EC2. No raw token output may reach logs. If the library cannot meet that policy, change the adapter or storage design before proceeding.

## Success Criteria and Verification

Engineering review approved deterministic failure tests plus live validation. The detailed branch map, assertions, proposed test files and failure matrix live in [engineering-test-plan.md](engineering-test-plan.md). Implement tests alongside each feature; real SQLite transactions, HTTP requests and process restart/crash behavior must not be hidden behind mocks.

- An operator signs in without creating any app registration; one DM and one triggered group message receive replies in the correct chats.
- Unlisted senders/chats, self messages, historical messages and untriggered group traffic cause zero OpenClaw requests.
- Two chats retain separate sessions; two accepted turns in one chat share history. Verify group sender attribution and dedicated-agent resource boundaries.
- Repeated pages, same-timestamp messages, pagination overlap, restarts and edited messages do not generate duplicate work in controlled tests.
- Fault injection before/after database commits, OpenClaw submission and Teams submission produces the documented retry/uncertain behavior.
- Test throttling, expired sessions, revoked chat access, long Unicode replies, queue saturation and account mismatch. Never claim continuous renewal from a short smoke test.
- Under normal connectivity and within the configured request budget, target enqueue within two polling intervals. Report budget saturation or throttling when that target cannot be met; end-to-end latency also depends on OpenClaw generation.
- A fresh clone has no secrets or organization identifiers and passes config-validation, router/state-machine tests, adapter contract tests with synthetic fixtures, lint, typecheck and build.
- Record a tenant-tested compatibility matrix: exact OpenClaw/client versions, OS, interactive login, DM/group behavior and an overnight run with session-expiry testing. Live tests are opt-in and use designated test chats.

## Distribution Plan

Public GitHub source, installation from tagged releases, and a versioned npm CLI package once ownership/name are confirmed. Propose MIT licensing, subject to owner confirmation and dependency license review. README covers limitations, login, configuration, allowed chats, OpenClaw setup, recovery and uninstall. Include CONTRIBUTING and SECURITY documentation and sanitized example configuration.

GitHub Actions runs checks and builds on PRs; synthetic fixtures only, no tenant credentials. A manually approved tagged-release workflow publishes the package using trusted publishing and attaches checksums/artifacts. Package contents are allowlisted and checked to exclude state/config secrets. No automatic public publication during design or implementation. Docker distribution is deferred until browser login and secure credential storage have a tested container workflow.

## Operator clarification after deployment (2026-10-03)

The intended integration exposes the existing OpenClaw agent through Teams, including its configured skills and tools, rather than maintaining a separate restricted agent. The operator explicitly authorized that capability sharing. The bridge therefore targets the existing agent via its authenticated Chat Completions endpoint; sender/chat allowlists remain in the bridge, and conversation history remains per chat. A dedicated agent/Gateway is an optional restriction for other deployments, not a requirement of this project. This clarification supersedes the earlier dedicated-agent deployment requirement.
